# 開発プロジェクト概要

## 1. 個人制作プロジェクト
### [F9engine]
* **GitHubリポジトリ:** [個人制作GitHubリンク](https://github.com/AkiraFuku/F9engineVer.0.git)
* **開発期間:** [2026年3月〜現在]
* **使用言語 / 環境:** C++, DirectX12, Visual Studio
#### 概要
3Dアクションゲームの制作を想定し、グラフィックス、物理判定、ゲームループ、オブジェクト管理をゼロから構築した自作ゲームエンジン。拡張性とパフォーマンスの両立をテーマに開発を続けています。

#### 主な機能・特徴
* **ポリゴンメッシュ対応の3Dレイキャスト物理システム:**
  ステージ上のTriangle（ポリゴン情報）を走査し、足元から下方に向けた正確なレイキャスト判定を行う仕組みを実装。ポリゴン表面（FrontFace）のみを最短距離で検出し、空中での重力加速度の適用や地面への吸い付き、めり込み補正などを自作物理ロジックとして実現しています。
* **レール追従型 3D全方位シューティング制御:**
  ステージに配置された3Dレール上を進行するProjectile（弾）の制御システム。レールの進行方向（XZ平面）への前進・後退だけでなく、上下入力を高度（Y軸）の速度成分として合成することで、うねるような3D構造のステージでも破綻せず直感的に上下左右へ撃ち分けられる弾道ロジックを構築しています。
  * **オブジェクト間衝突をトリガーとした「ロボット強奪・搭乗システム」:**
  ゲームの核となる固有ギミックとして、エネミーとの衝突判定と状態遷移を完全に連動させたシステムを実装。プレイヤーが通常状態で突進攻撃を仕掛けると、エネミーを「スタン状態」に遷移させることができます。さらに、スタン中のエネミーへ追撃（再衝突）することで、エネミーが内部に保持している「ロボット（Robot）」データを奪い取り、プレイヤーのステートを強制的に「搭乗状態（RideOn）」へと変身・遷移させるダイナミックなゲーム性をプログラム側から支えています。
* **State × Behavior × Command パターンによる高度なゲームオブジェクト制御:**
  プレイヤーおよびエネミーに対し、「状態（State：通常・搭乗・スタン・死亡）」と「行動（Behavior：パトロール・ルート・攻撃・ジャンプ・照準）」を分離して管理する2層構造のステートマシンを共通設計として導入。入力や挙動の命令を `ICommand` を介して抽象化し、各オブジェクトの独立性を高めることで、複雑に絡み合うキャラクター同士のインタラクションをクリーンに記述しています。

#### こだわった点・苦労した点
* **3D空間における正確な接地と地形追従の実現:**
  単純なBounding Boxによる判定ではなく、モデルのポリゴンデータを直接利用したレイキャスト判定に挑戦しました。最短交差距離の計算や重力加速度のシミュレーションにおいて、高速移動時にもキャラクターが床を突き抜けないよう、フレームレートに依存しないめり込み補正計算のロジック構築に最も苦労し、結果として安定した操作感を実現しました。
#### 今後実装したい機能・改善点
* **空間管理（空間分割）によるレイキャスト物理の軽量化:**
  現在はステージ上の全ポリゴン（Triangle）を毎フレーム走査してレイキャスト判定を行っているため、広大なステージでは処理負荷の増加が懸念されます。今後はOctree（八分木）などの空間分割アルゴリズムをエンジンに組み込み、プレイヤー周辺のポリゴンのみに判定を絞り込むことで、物理演算の大幅な高速化・最適化を図ります。
* **搭乗ロボット（Robot）の種類拡張とデータ駆動型のステート生成:**
  現在はテスト用のライドオン状態（StateRideOnTest）を単一で生成する仕組みですが、Robotインターフェースの拡張性を活かし、「高火力型」「スピード型」など性能やアクション（Action）が異なる多様なロボットを量産します。また、パラメータを外部ファイル（JSON等）からロードして動的にステートを生成するデータ駆動型の設計へのアップグレードを目指します。
* **Behaviorパターンと連動した「汎用死亡・被弾演出システム」の構築:**
  現状、プレイヤーやエネミーの死亡状態（StateDead）における演出ロジック（非アクティブ化への移行タイマーや専用エフェクトの発生など）が一部未実装、またはクラス内に個別記述されています。これらをBehavior側でアニメーションやパーティクルエミッタと綺麗に同期させ、汎用的な演出フェーズとして共通化・実装を完了させます。

## 2. チーム制作プロジェクト
### [TD3 4ヶ月開発作品：タイトル「クモり」]
* **GitHubリポジトリ:** [チーム制作GitHubリンク](https://github.com/AkiraFuku/TD3_4monthDevelop.git)
* **開発期間:** [例：2026年2月〜6月（4ヶ月間）]
* **チーム構成:** [例：プログラマー4名]
* **担当部分:** [ゲームエンジンとキャラクターのアニメーション]
* **使用言語 / 環境:** C++, DirectX12, Visual Studio
#### 概要
独自のゲームエンジン（自作アニメーションシステム等）をベースに開発した、4ヶ月間のチーム制作ゲームプロジェクト。プレイヤーが「糸」や「物を運ぶ」といったギミックを活用しながら進めるアクション要素を含む作品です。

#### 担当した主な実装機能
* **[ゲームエンジン]:** []
* **状態遷移ベースの汎用アニメーションシステム（Anima）の設計・実装:**
  プレイヤー、エネミー、オブジェクト（卵など）で共通して利用できる軽量なアニメーション制御機構を構築。
* **プレイヤーのアニメーション実装（PlayerAnima）:**
  待機（Idle）、歩行（Walk）、運搬（Carry）、糸乗り（OnThread）、ステージクリア（Clear）など、ゲーム進行や操作に連動した多彩なモーション（Lerp/Slerp補間）を実装。
* **エネミーおよびオブジェクトの挙動制御（EnemyAnima / EggAnima）:**
  エネミーの待機・跳ねる移動（Walk）・クォータニオンによる大きく振りかぶる攻撃（Attack）モーションや、ギミック対象となる卵が左右に揺れるアニメーションなどを実装。
#### チーム開発における工夫・成果
* **クォータニオン計算のキャッシュによるパフォーマンス最適化:**
  腕などの複数パーツが高速で回転連動するアニメーション（CarryやOnThreadなど）において、毎フレームのクォータニオン計算を事前にキャッシュ化して球面線形補間（Slerp）に適用することで、処理負荷を軽減しゲーム全体の安定動作に貢献しました。
* **デザイン・調整フェーズを意識したメンバ関数とデバッグ環境の提供:**
  外部（他プログラマーやデザイナー）から各キャラクターのモーション再生速度（`SetAnimationSpeed`）やワンショットアニメーション終了後の遷移先（`SetOneShotFinishState`）を容易に変更できるよう関数を共通化。また、ImGuiを用いたリアルタイムなアニメーション状態の可視化を行い、チーム内での挙動調整をスムーズにしました。
